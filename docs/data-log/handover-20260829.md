### `references/writing-rules.md`

- **受賞は「書くな」ではない。** 大会名・年・部門が揃うものは紹介文の骨にしてよい。
  禁じているのは「カードに無い受賞」と「大会名も年も無い宣伝文句」
- **販売地域・販売形態は本文に書かない。** カードには記録するが、公開後に崩れる事実だから
- **伝聞逃げを消すことと、事実にすることは別。** 断定してよいかは語尾ではなく事実の側で決まる。
  あわせて「一括修正の例外に気づいたら、既に適用した分を全部見直す」

### `references/fields.yaml`

- `ProductExplain` の `min_length` を **120 → 80**。事実が薄い銘柄で120字を満たそうとすると
  一般論で埋めるか出典をなぞるかしかなくなり、**監査が繰り返し指摘した欠陥を検証が要求していた**

### `scripts/check_facts.py`(**新設**)

事実カードの語リストに助詞・比喩の言い回し・長すぎる文字列が入っていないかを検査する。
**検出専用で自動修正はしない** —— 一度 `--fix` を実装したが、正規表現では語を選べず
「のど越し」→「ど越し」、「まろやかな味わい」→「味わい」といった改悪が9件出た。
出典を持ち、どの語がその銘柄を表すか選べるのは収集役だけ。**検出したら差し戻す。**

```bash
cd /workspace/tool/beer/beer-data-work
python3 /workspace/.claude/skills/beer-data-pipeline/scripts/check_facts.py facts-3b
```

### `scripts/validate.py`

- **出典の要否を候補一律ではなく `fields.yaml` の `needs_source` に従わせた。**
  スタイル解説49件が全件「出典が無い」で不合格になっていた
- `op=update` のスタイル候補は**現行行を下敷きに**分類判定する

## 7. このセッションで学んだこと(再発しうる)

### 7-1. 文章で書いた規律は守られない

「拾うのは語だけ。言い回しごと持ち込まない」(§5-1)は3バッチ前から明記してあり、
**3バッチ連続で守られなかった**。監査の指摘のほぼ全部がコピー性で、出所はすべて事実カード。
執筆役は Web 取得手段を持たないのに、**カードが原文の言い回しを運べば原文が再生産される**。

`check_facts.py` という機械検査にして、ようやく 0件になった。
語配列の機械整列を入れたときと同じ構図。**規律は文章ではなく検査で実装する。**

### 7-2. 検証が規律を否定していた箇所が3つあった

- `ProductExplain` の下限120字 —— 事実が薄い銘柄で満たそうとすると一般論で埋めるしかなく、
  **監査が繰り返し指摘した欠陥を検証が要求していた**
- 出典の要否 —— `fields.yaml` が `needs_source: false` と定めた項目に、検証が一律で出典を要求。
  **規律が「不要」と定めたものを検証が要求すると、書き手は出典を捏造するか作業が止まるかしかない**
- 伝聞逃げの語彙が「とされる」だけで、連用形「とされ」が3件すり抜けた

### 7-3. オーケストレーター(私)が最大の違反者だった

過去3バッチとも、**最も重い指摘は私の判断に対して出ている**。
自分で確かめるより、ブリーフに「私がやった変更の一覧表」を置いて監査役に名指しで
検証させるほうが確実だった。

実際にやった誤り:

- **§5-1-6(分類を変えたら依存する値も見直す)を書いた当人が、同じ周回で4件見落とした**
- `check_facts.py` の `--fix` で9件のカードを改悪(「のど越し」→「ど越し」)
- 検査の誤検出で正当な語が失われ、収集役がデータのほうを曲げた
- `/products.json` に仕様欄が無く22件で度数が欠落
- 禁止リストに「受賞」を入れ、受賞そのものが禁止だと読まれた
- ブリーフで `catchcopy` の上限を120字と書いた(`fields.yaml` は20字。DBカラムを見ていた)
- 正規化していない元ファイルから統合し、直した箇所が戻った

### 7-4. 一括修正の例外に気づいたら、既に適用した分を全部見直す

伝聞逃げ「とされる」を3件まとめて断定に直したが、うち `Saison` の農家起源譚は
**古い史料には現れず、1980〜2000年代のマーケティングで再構成された物語**だった。
逃げを消した結果、**神話を史実として発信する**形になった。

しかも同じ周回で `English-Style IPA` の「インド航路」で**まったく同じ罠に気づいて
因果を落としている**のに、**先に直し終えていた分を見直さなかった**。

### 7-5. 条文をバッチ途中で足すと、その後に再処理された候補にしか届かない

販売地域・販売形態の禁止条を3社バッチの途中で足したため、
**round2 の書き直し対象に入った銘柄だけ直り、それ以外に残っていた**。
横断検査で4件の残存を検出。該当は**すべて書き直し対象外**だった。

**バッチ途中で条文を足したら、その時点で全件を洗い直す。**

### 7-6. 仕事の性質でリスクの所在が変わる

| 仕事 | 出典 | 最大のリスク | 監査の道具 |
|---|---|---|---|
| 銘柄の紹介文 | 公式ページあり | **コピー性** | ローカル控えの Read(WebFetch は要約が挟まるので不可) |
| スタイル解説 | **無し**(`needs_source: false`) | **出典を持たない断定** | **WebFetch で事実の裏取り** |

スタイル解説では実在しないホップ品種名が実際に出た。**書き手は間違っていても
文章の見た目が変わらない。**

### 7-8. 仕事ごとに risk の形が変わる(3種類そろった)

| 仕事 | 出典 | 最大のリスク | 監査の道具 |
|---|---|---|---|
| 銘柄の紹介文 | 公式ページあり | **コピー性** | ローカル控えの Read |
| スタイル解説 | **無し**(`needs_source: false`) | **出典を持たない断定** | **WebFetch で事実の裏取り** |
| ブリュワリー解説 | 公式ページあり | **創業年と醸造開始年のすり替え** | 両方(ただし EUC-JP は控えのみ) |

**監査ブリーフの冒頭に「この仕事で最大の危険」を書くと、指摘の質が変わる。**
ブリュワリー解説では7社の年の対応表を先頭に置いた結果、**7社すべてで分離が維持された**。

### 7-9. API 障害が続くときの対処

このセッションでエージェントが **8回** `Connection lost mid-response` で落ちた。
観察したこと:

- **落ちるのはほぼ最終報告の生成中。作業自体は終わっていることが多い。**
  必ず**出力ファイルの有無を確認してから**起動し直す(ベアレン19件の事実カードはこれで救えた)
- **担当を小さく割ると生存率が上がる。** 6社→3社に割ったら通った。
  5社が落ちた作業を4社+1社に割ったら両方40〜50秒で完了した
- **「報告は3行以内で」と明示すると通りやすい**(報告生成が長いほど落ちる)
- ブリーフと割り当てファイルを**ファイルに書き出しておけば**、起動し直しは安い。
  失われるのは実行時間だけ

### 7-7. 分業の設計

- **役の隔離は、渡すデータの粒度まで設計しないと迂回される**
- **エージェントが「できない」と正しく報告したものは、道具を持つ側が引き取る**
  (年齢ゲート・EUC-JP・座標の確定はオーケストレーターの `curl` で解決した)
- **統合と正規化は必ず1手順にする**(分けると正規化が再統合で消える。2回踏んだ)
- **エージェントの報告も鵜呑みにしない**(タイムゾーンの取り違え、権威ある出典と
  突き合わせない座標判定、使ってはいけないと明記したフィールドを根拠にした乖離報告)
- 銘柄の執筆は**蔵を混ぜて**配る(同じ蔵が並ぶと構成が揃う)。
  スタイル解説は逆に**系統ごとにまとめて**配る(隣との書き分けが成果物だから)
