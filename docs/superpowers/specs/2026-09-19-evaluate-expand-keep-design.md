# 評価・拡張・保管 — 動線の設計

2026-09-19 / ブランチ `renewal` / 対象 https://drtbeer.com

**この設計書は `2026-09-16-photo-recommender-design.md` の §3(画面の流れ)と §6(確度による分岐)を
置き換える。** それ以外の節(データの持ち方・推薦ロジック・費用の上限・PR枠・デザイン)は引き続き有効。

## 1. なぜ書き直すか

計画1の中核を dev に載せ、利用者が自分のスマホで実際に使った。動きはしたが、
**「あっけない」**という実感が返ってきた。写真を上げて、銘柄名が出て、似た3本が並んで終わる。

原因ははっきりしていた。**この機能がやっている判断が、画面に出ていない。**
実際には「同じ New England IPA の中から、別の蔵のものを選ぶ」という仕事をしているのに、
`Similar` という英語の見出しの下に3行並ぶだけだった。

そこで、利用者にとっての価値を3つに定義し直す。

| | 価値 | 中身 |
|---|---|---|
| **A 評価** | アップロードされたビールが**どんな特徴を持つか**を、**クラフトビールのユニバースに照らして言語化する** |
| **B 拡張** | 評価に沿って、**利用者の声**(もっとフルーティーに / もっと軽く)で絞り込み、体験を広げる |
| **C 保管** | A・B で得たものを **LINE を通じて残し**、継続的な体験にする |

**推薦は目的ではなく、評価の結果として出てくるもの**になった。順序も変わる
(以前は判定→推薦→確認。これからは判定→**評価**→**保管**→推薦)。

## 2. 動線

```
① 写真 または 銘柄名のアップロード
        ↓
② 解析          — 生成AIに画像を渡す(2〜5秒)
        ↓
③ 評価          — このビールがどんな特徴を持つか(A)
        ↓
④ 保管(任意)   — 評価と自分の感想を残す。LINE で紐づける(C)
        ↓        ※ 飛ばして⑤へ行ける
⑤ 拡張          — 「もっと〜」で絞り込みながら次の一杯を探す(B)
```

### ④を⑤より前に置く理由

**感想がいちばん新鮮なのは、評価を見た直後**だから。推薦を見たあとだと、
「このビール自体の感想」が薄まる。

ただし**④は任意で、飛ばせる**。⑤がこの体験のいちばんの報酬なので、
**その前にログインの壁を立てない**。「感想を書く」ところまでは匿名でもでき、
**実際に残そうとしたときに初めて LINE を案内する**。

## 2-b. ② 解析 — 宇宙に投げ込む

解析には2〜5秒かかる。いまは「判定しています…」という文字だけで、**その間が空いている**。

ここに**味覚の宇宙へ1点が投げ込まれる絵**を置く。

**これは飾りではない。** `assets/js/galaxy.js` には既に、200銘柄が度数・苦味・フルーティーさの
座標に浮かぶ宇宙がある。③の定義が「**クラフトビールのユニバースに照らして言語化する**」である以上、
**照らし合わせている様子をそのまま見せている**ことになる。待ち時間が説明に変わる。

### 作り

- 送信した瞬間に**全画面の暗い canvas** に切り替える(露光案の地と同じ純黒)
- 既存の星々を**減彩の色**で薄く漂わせる(スタイルグループの通常色)
- そこへ**1点が外から飛び込み**、減速して星々の中に落ち着く
- **飛び込む1点だけが強調色**。設計書 §11 の「強調を使ってよい3か所」に、
  この1点を加える(同定された1本のハローと同じ扱い)
- 応答が返った時点でブラウザが遷移するので、**終わりの尺は決めない**。
  長引いても自然に回り続ける作りにする

### 制約

- 解析はフォームの送信中に起きる。**送信を JS で受けて全画面に切り替え、
  応答が来たら遷移する**形にする(通信をやり直さない)
- **JS が動かない端末では絵は出ない。** そのまま待つだけになるが、送信は通る
- 3D の本体(`galaxy.js`)をそのまま持ち込まない。**軽い2Dの星野で足りる**。
  読み込みが重いと、待ち時間を埋めるはずのものが待ち時間を作る

## 2-c. これまでの保管データへの導線

トップから**これまでに撮ったビール**へ行けるようにする。

**ただし目立たせない。** この画面の主役は「ビールを読み込むこと」であり、
履歴はそのあとに生まれる副産物である。

- トップの**下のほう**に、小さく `これまでの ○本 →` と出す
- **写真が0枚の人には何も出さない**(空の入口を作らない)
- 押すと**一覧**へ。撮った日・銘柄名・評価の要点が並ぶ

### 匿名でも見える

**LINE ログインは要らない。** Cookie があれば自分の記録は見える(§4 のとおり)。

**この一覧が、LINE を案内する自然な場所になる。** 一覧の下に
「**別の端末でも見るには**」として LINE 連携を置く。価値が目の前にある場所で誘うので、
④の「残しますか」と合わせて**2か所**から入れる。

## 3. ③ 評価 — 何を、どう言うか

### 軸は3つ

| 軸 | 出どころ | 状態 |
|---|---|---|
| **度数** | `products.Alcohol` | 197/200(98%)。0.5〜11.0% と幅が広い。**測定値** |
| **苦味** | `products.IBU_all` | 196/200(98%)。8〜90。**一部は推定**(`estimated_fields` に記録済み) |
| **フルーティーさ** | `products.Fruity` | **付け直しが必要**(§7)。現状は1〜4で平均2.1、ほぼ全銘柄が同じ箱に入る |

**色と透明度は主軸にしない。** 埋まっているのが 52% / 43% しかなく、語れない銘柄が半分ある。

### 言い方 — 断定ではなく、比較として言う

実データで試したところ、**断定すると一般感覚とずれる**ことが分かった。
度数 5% の銘柄が「とても軽い」と出る。クラフトビール200銘柄は度数が高いほうに偏っている
(平均5.7%)ので、**このユニバースの中では正しい**が、読み手は違和感を持つ。

そこで、**何と比べているかを必ず添える**。

> 苦味は **ほどよいほう**。200銘柄のうち、これより苦いものが 71%。(IBU 25)
> 度数は **軽いほう**。これより軽いものは 12%。(5.0%)

こう書けば、ユニバースに照らすという狙いを保ったまま、断定による嘘が消える。

### 文はデータから規則で作る。モデルに書かせない

**この案件は、画面が嘘をついた不具合を3回直している**
(URLを打つだけで「記録しました」/ 控えていないのに「控えておきます」/
未登録なのに確認だけ出す)。評価は体験の核なので、**構造的に嘘をつけない作り**にする。

- 測った値・推定した値を、**規則で言葉に翻訳する**だけ
- 同じ入力からは**必ず同じ文**が出る
- **追加の費用はゼロ**
- モデルには書かせない

### 未登録のビールも評価する

`products` に行が無いビールでも、**モデルが推定した値で同じ文を出す**。
ただし **「ラベルからの推定です」と明示する**。

これは必須である。実際に上がった最初の1件(SUPERFLUX / バンクーバーの蔵)が未登録だった。
200銘柄に対して世の中のクラフトビールは桁違いに多いので、**未登録のほうが常態**になる。
ここで弾くと入口が成立しない。

### 読み取りが確かでないとき

旧設計 §3 が**肝**としていた「外したときに黙って誤った推薦を出さない」は引き継ぐ。
置き場所が変わるだけで、なくならない。

| 状態 | 画面 | 裏でやること |
|---|---|---|
| **ビールに見えない** | 撮り直しを案内。評価もしない | **画像を保存しない**。記録は残す |
| 銘柄を特定できた | 評価を出し、**その下で確認を求める** | `upload` に記録 |
| 銘柄名は読めたが未登録 | 評価を出す(推定の旨を添える)。**「まだ登録がありません」も伝える** | `unknown_beer` に記録 |
| **銘柄名も読めない** | 読み取れたスタイル・特徴で評価を出し、**確認を求める** | 確認の結果を記録 |
| **確度が中くらい**(0.4〜0.8)で候補が複数 | **候補を並べて選ばせる**。選んでから評価へ | 選んだ結果を記録 |

**確認は③の中に置く。**「この評価で合っていますか」という形になり、
旧設計の「この銘柄で合っていますか」より自然に収まる。

**確認の答えは、④の保管とは別物である。** 確認は読み取りの正しさを問うもので、
保管は感想を残すもの。**確認を押さずに④へ進めてよい**。

### タイプ(MBTI的なもの)

「このビールはこういうタイプ」という性格づけは**後で真面目に定義する**。
いまは入れない。入れるとしても、上の3軸から**規則で決まる**ものにする。

## 4. ④ 保管 — 感想を残し、LINE で紐づける

- 評価の画面から、**感想を書く欄**を出す(任意)
- 書いた感想は**匿名のまま保存される**(いまの訪問者IDの仕組み)
- 「**残す**」を押したときに初めて **LINE ログイン**を案内する
- **飛ばして⑤へ行ける**

### LINE 連携は実地で確認済み(2026-09-19)

dev で最小の往復を通し、3つの未知を解いた。

| 確かめたこと | 結果 |
|---|---|
| dev の Basic認証を挟んだまま LINE から戻れるか | **戻れる** |
| 利用者IDは端末をまたいで同じか | **同じ**。PC とスマホで同一のIDが返った |
| 匿名の記録が引き継がれるか | **引き継がれる**。写真2枚とイベント6件が合流した |
| 費用 | **無料**(課金は Messaging API の通知。今回は使わない) |

**制約が1つある。ログインの誘いは「使っている画面の中」に置くこと。**
別の場所で URL を開かせると、その端末の匿名の記録が孤児になる。
実際、PC から先にログインしたため、PC 側には何も無いまま紐づいた
(あとからスマホでログインして合流できたが、順序が逆なら失われていた)。

### 別の端末から来たとき

- **Cookie が生きていれば**、ログイン不要でそのまま見える
- **新しい端末・Cookie を消した場合**は、最初は何も見えない。
  その端末で LINE ログインすると、**同じIDだと分かって過去の記録に合流する**
- **自動では認識しない。** Cookie が無い状態では相手が誰か分からないので、
  LINE ログインが「私です」と名乗る唯一の手段になる

### プロバイダーの置き方(2026-09-19 決定)

LINE の利用者IDは**プロバイダーごと**に発番される。
同じプロバイダー配下のチャネルどうしなら同じIDが返るが、**別プロバイダーでは別IDになり、
あとから同一人物だと突き合わせる手段はない**。

- プロバイダー **`Beer Projects`** を1つ作り、その中にサービスごとのチャネルを並べる
- 最初のチャネルは **`drtbeer`**(LINEログイン / ウェブアプリ)
- 将来の**訪日外国人向けの蔵紹介サイト**(`docs/next-ideas.md`)も同じプロバイダーに入れる。
  利用者から見て地続きの世界だから
- **無関係なサービスは別プロバイダーにする。** 技術的には繋げられるが、
  利用者が知らないうちに同一人物として突き合わせられるのは説明がつかない

**分けるのは後からできる。まとめるのは後からできない。**

## 5. ⑤ 拡張 — 「もっと〜」で絞り込む

### 決まったボタンで受ける

自由記述はいまは作らない。**方向は数個しかない**ので、ボタンで足りる。
1回ごとの課金も発生せず、押された内容が**そのまま蔵向けの数字になる**。

| ボタン | 何をするか |
|---|---|
| もっと軽く | 度数が低いほうへ |
| もっと強く | 度数が高いほうへ |
| もっと苦く | 苦味が強いほうへ |
| 苦味は控えめに | 苦味が弱いほうへ |
| もっとフルーティーに | フルーティーさが高いほうへ |

押すと、**基準の1本を「押した方向へずらした仮の1本」に置き換えて**、推薦を引き直す。
段階カスケード(設計書 §5)はそのまま使う。

**自由記述は、必要になったら足す。** ボタンでは表せない要望が実際に出てきてからでよい。

### 押した内容は記録する

`event` に種別として残す。**何が求められているかは、蔵に売る分析の中身そのもの**になる。

## 6. 推薦に理由を添える

**あっけなさの正体**だったところ。`$picked` の各要素は `stage`(カスケードの何段目で拾ったか)を
持っているのに、画面で捨てていた。

| 段階 | 何と言うか |
|---|---|
| 1 | 同じ **<スタイル名>** から |
| 2 | 同じ **<系統名>** の系統から |
| 3 | 近い味わいのものから |
| 4 | 度数が近いものから |

加えて、**「別の蔵を優先している」ことを一言**添える。これがこの機能の判断そのものであり、
黙っていては伝わらない。

## 7. ③の前提 — フルーティーさを付け直す

**いまの `Fruity` は軸として機能していない。** 1〜4の4段階で平均2.1。
実データで試すと、ほぼ全銘柄が「控えめ」に落ちる。

### モデルに200銘柄を採点させる

度数と苦味は**測った値**だが、フルーティーさは**感じ方**で、測定値が存在しない。
アップロードされたビールは**モデルに推定させるしかない**(未登録なら特に)。
だとすれば、**比べる相手の200銘柄も同じ物差しで測る**べきである。
片方を人手の4段階、もう片方をモデルの推定にすると、**物差しの違うものを比べる**ことになる。

- 材料は各銘柄の `ProductExplain`(自分たちで書いた紹介文。香りや味に触れている)と `StyleName`
- **1〜10** で付ける(いまの4段階より刻みが細かく、⑤の絞り込みが効くようになる)
- **推定であることを `estimated_fields` に記録する**(この案件の既存の規律)
- 費用は15〜30円程度の見込み
- **データの仕事なので `/beer-data-pipeline` の枠組みで別に走らせる**

この作業が終わるまで、③のフルーティーさの行は出さない。

## 8. この設計で作らないもの

- **自由記述による絞り込み** — ボタンで足りないと分かってから
- **タイプ(MBTI的なもの)** — 後で真面目に定義する
- **色・透明度を主軸にした評価** — データが半分欠けている
- **Messaging API による通知** — 有料。LINEログインだけで足りる

## 8-b. 実装の規模について

この設計は**2つの独立した仕事**を含む。実装計画は分けて書く。

1. **フルーティーさの付け直し**(§7)— データの仕事。`/beer-data-pipeline` の枠組み。**③の前提**
2. **動線の作り直し**(§2〜§6)— ②解析中の絵 / ③評価 / ④保管 / ⑤拡張 / 推薦の理由 / 履歴一覧

いま進行中の**計画2(公開できる状態にする)とも衝突する**。
計画2のタスク7(トップ差し替え)と8(候補3件の画面)は、この設計に合わせて書き直す必要がある。
**計画2をどこまで進めてからこちらに移るかは、実装計画を書く前に決める。**

## 9. 持ち越し・注意

- **空の訪問者の行が溜まる。** ページを開いただけで `visitor` に行ができる。
  dev で6行中5行が写真0枚だった。いまは実害ゼロだが、いずれ掃除が要る
- **`line/` のいまの実装は spike。** 「繋がるか」を確かめるために書いたもので、
  `try.php` からの導線も、感想を書く画面もない。動線に組み込むときに書き直す
- **LINE チャネルは作成直後「開発中」で、作成者以外はログインできない。**
  prod に出すときに「公開」へ切り替える
- **`Fruity` の付け直し(§7)が③の前提。** 先に済ませる
